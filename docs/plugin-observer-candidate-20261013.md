# 插件更新入口候选：当前证据与完成条件

当前目标仍是本人四类命中结果进入已有两秒收纳绶带。0.4.22 已安装并通过短时调度诊断，它不产生命中记录。

## 已确认

- 当前 GameDLL 唯一命名导出是 `get_plugin_api`，实际目标 RVA `4EEAD0`。已读导出表与展开代码，不执行 getter。
- getter 的前 173B 控制流有两条已闭合路径：编号 0 初始化 11 个函数槽并返回 `Game+37CEB10`；其它编号返回 NULL。这是实际代码事实，不依赖公开 SDK 的表偏移。
- 实际返回表的 200B 前后相同，11 个已知函数槽全都匹配 getter。槽 `+68` 指向 `4EE6C0`。
- `4EE6C0` 的已解释 67B 路径保存入站浮点帧间隔，并以 `[Game+3326340]` 为 context 调用 `AB5000`，随后尾转移到 `173BAB0`。另外两次间接调用的合同未知。

导出、getter、表和入口分别保存于 `dist/hit-game-plugin-export-live-20261013-v1`、`dist/hit-game-plugin-entry-window-live-20261013-v1`、`dist/hit-game-plugin-table-update-live-20261013-v1`。三次采集均在真实 TitleScreen，前后 PID、context、模块身份和代码校验一致。它们不是战斗事件样本。

## 尚未证明

1. 引擎持续读取表还是缓存新入口的具体机制。短时替换已确实被调用，但不能据此推导完整插件 API 合同或帧率。
2. 更新前后是否仍能看到完整碰撞结果：有效 AP、装甲、强制/自定义原因、本人 peer，以及真实物理跳弹。
3. 这些结果是否有稳定序号和完整生命周期，足以避免漏记或重复。

公共 Stingray SDK 说明插件接口采用函数表，且提供逐帧更新回调，但不能直接移植其字段排列到 HD2。[原 SDK 头文件](https://github.com/AutodeskGames/stingray-plugin-api-samples/blob/master/stingray_sdk/engine_plugin_api/plugin_api.h)

## 唯一下一诊断

碰撞父片段的 104B 和后续 gap 168B 已补齐，与旧 owner 材料拼接出连续入口。已确定 `R15` 保存当前处理对象，`R15+E7040` 为 work 数量，真正 work row 起于 `R15+E7044`，步长 32B。row 的 `+00` 是 pool slot，`+04/+08` 为两组外部记录索引；如果以计数容器为起点，则这三项相应为 `+04/+08/+0C`，不能混用相对基址。已有代码未证明输入就绪时机、消费/清空出口或结果持久保留。

当前唯一诊断是先准备插件更新表的短时计数观察，确认引擎是否真的使用该槽。自有进程原型已经通过：14B wrapper 只增自有计数并尾调用原函数；浮点输入/结果和原 callback 次数保持；恢复 CAS 不覆盖第三方接管；代码及数据页保留到进程结束使旧缓存入口仍有效。证据在 `dist/frame-counter-tail-owned-20261013`。

游戏中的槽页已只读确认是 RW，但这不证明写入被允许。`src/native-plugin-frame-probe.lua` 已接入 0.4.22：只在 Title/Ship 且读取接口就绪时尝试一次；核对模块身份、源码、导出、11 个表槽和原值后，用 CAS（仅原值仍相同时替换）安装 14B 自有计数入口。窗口约两秒，依赖 MOD 的后续 tick；终止时按所有权恢复，失败则显式重试清理，不缓存为完成。两个自有页面保留至进程退出，避免缓存入口失效。终止后 MOD 不再采样；若引擎另有缓存入口，晚调用仍会增加自有计数后转发，不能声称完全没有该指令的持续开销。诊断写入独立存档，不进入 `last_mission` 或战争账单。

真实同版本 LuaJIT 的自有进程测试已通过计数、浮点输入、恢复、第三方接管保护及终止后零读取；源码身份使用保存夹具，并非游戏调用证据。探针只回答引擎是否调用该入口，不读取 contact payload、不改游戏代码页；四类命中、生涯自动同步和帧数均未因此获得实机证明。
