# FIRE 持续燃烧漏计：一次代码诊断

当前FIRE按火焰武器/战备来源累计。用户已确认部分持续燃烧死亡漏计；旧记录不足以确定漏计数量，不能把总击杀差额补成火死。

`tools/fire_code_capture.py` 是独立Python采样器，等待正常启动游戏，在模块加载后等待20秒，再读取三个固定代码窗口。舰上即可，不依赖Codex，不需要地图或烧死敌人。只读19,328字节，分六段，每段最多4KiB并间隔0.1秒；18处已有代码特征直接在这些字节中核对，不再读取正文。

采样器不设置等待游戏的120秒截止。实际采集最多两次尝试；成功后退出，之后再次启动会核对旧材料并直接结束。不创建常驻游戏回调，不改变游戏状态或已安装MOD。Windows句柄权限仅为读取/查询（0x410）。本机EXE/DLL的SHA256先核对，模块真实路径和映像大小再核对；采集前后确认模块身份和磁盘文件戳，六段使用同一进程句柄。

结果在项目 `dist/fire-code-capture/`：一份合并BIN、一份含窗口偏移/长度/18特征/哈希/读取耗时的JSON，以及`status.json`。`complete`代表研究材料已通过核对，不代表FIRE计数已修复；这也不是同一帧的战场数据（`atomic=false`）。本机真实读取已成功，FPS未验证。

若未启动后台采样器，可双击项目根目录“启动火焰诊断.cmd”，再正常启动游戏。窗口等待时可关闭Codex，Ctrl+C可取消。成功材料会保留；不用重复采。此工具不启动或关闭游戏。

材料用于核对最终死亡时healthExt的kind/element写入与覆盖规则，再确定如何与已有火焰来源击杀去重。现有火焰武器/燃烧战备的直击口径保持；不按当前手持武器、曾经挂火或时间接近推算火死。

验证：12项测试通过，包括固定六段/19,328字节、18特征、短读拒绝、不可读内存拒绝、成功缓存、等待超过120秒、两次失败停止，以及Windows自身进程模块/缓冲区读取。测试没有读取游戏。

完整死因setter已证明：owned目标第一次进入dead=2时保存致死kind/element，后续同一life不覆盖；这两个字段未同时保存武器来源。AddStat的main/source分支单次互斥，不能推出火焰致死与火源白名单统计互斥。当前不能可靠合并这两类累计值；FIRE仍未修复，下一研究是同时获得死因、最终来源和归属的原始事件接口。没有新增游戏内回调或MOD改版。
