# 坦克命中来源与完整哈希补名（0.4.47）

## 坦克炮和同轴机枪

旧版原生命中资格表只列出 91 个已知个人/支援弹丸武器来源。TD-220 堡垒主炮和同轴机枪不在其中，因此即便原生命中已给出本人的 creditor，仍会被来源资格检查跳过。

本版只增加以下三个完整资源身份：

| 完整 64 位资源哈希 | 含义 | 证据 |
| --- | --- | --- |
| `1FA1F596769225C2` | TD-220 主炮挂载武器 | Runtime `vehicle_weapon_authoring` 中 attackResource、resources 与 mountPath 一致；primary 为 Projectile |
| `439F9E65C18567DA` | TD-220 同轴机枪挂载武器 | 同上，独立的第二个 Projectile 挂载 |
| `16474112801385B6` | 两个挂载共同的 TD-220 父载具 | 上述两条 mountChain.vehicleResource 完整相等；用于可能按父载具提供来源的原生直接弹丸接触 |

父载具哈希已在本机来源统计里出现，但**尚未在实战中抓到对应 HitInfo.source**。其准入属于已审核的来源别名覆盖，不代表已经确认游戏每次按哪一层归因。若原生 creditor 未明确指向当前本人，依然不计数；不以载具创建者、驾驶员、附近玩家或网络实体属主代替实际射手。

新增配置 `native-hit-vehicle-source-profile-v1.json` 从冻结的活体检查配置派生，只扩来源表 91 → 94，并把原 `qualifier_types` 中相应列表长度立即数同步改为 94。所有采样入口、原生穿甲结果、反射入口、提交队列、peer/epoch、目标存活检查保持原字节。普通接触仍需原生直接弹丸与护甲结论成立；不会用来源统计的 hit 总数冒充跳弹或击穿，也不把爆炸范围伤害追加为直接命中。

`tools/native/test_hit_copy_vehicle_source_owned.py` 在测试进程自有内存中执行这些已生成原生入口，覆盖旧版拒绝、更新后本人活敌接触通过、队友/零 creditor/尸体/未知来源拒绝，共 30 项；没有读取游戏或执行捕获的游戏代码。另验证新配置只有源长度一个立即数字节变化。实机位置、载具实际接触字段与计数仍需游戏内观察。

## 完整哈希补名

用户提供的[公开哈希表](https://docs.qq.com/sheet/DQ3Rya0VudGd3WWtv?tab=000001)在 2026-10-15 读取。表中的身份是无符号 64 位十进制字符串，使用 Python `int` 精确转为 16 位大写十六进制；不经过浮点数，不使用前缀、尾部、截断低 32 位或相近时间匹配。

`resource-hash-aliases.json` 包含 1184 个无歧义标签；一个相同哈希有不同文字的条目暂不采用。仅提取已声明“哈希值”列及紧邻的中英文名，备注不作为逻辑或指令。

`tools/resource_hash_labels.py` 只为 Runtime 原始类型表明确 `kind=enemy` 且 `kill=true` 的资源补入敌人表，本次补入 36 个原来未接入的敌人资源。已有审核名称和分类保持原样。没有体型证据的条目显示未知体型，不因此增加重型或巨型绶带；三种已审核的武斗/食腐变体沿用同族轻/中型分类。其他无歧义哈希也加入显示名称回退表，分类保留 unknown；资源统计的标签可以属于载具、敌方单位、鹈鹕或爆炸筒，补名本身不把它们分类成玩家手持武器。对于这些仅有标签证据的条目，武器类别必须有 SDK 完整资源哈希对应，不能仅凭与 SDK 武器英语同名就补成主/副武器。

旧记录只有保留完整资源身份才能补名。武器统计与 `unknown_unit_kills` 中保存的完整哈希可以在读取时重新对齐；只有“未知”总量而没有原始身份的部分无法恢复。旧死因采集在未识别类型时丢弃过该哈希，本版改为保留经过验证的 `evidence.actor_type_hash`。死亡观察器可选接入 `resource_names`，让非敌人资源通过完整哈希显示如“爆炸筒”的名称；类别与可信度仍保留 unknown，不补致命武器和伤害类型，有矛盾的玩家证据不采用别名。死因补名仍保留原有低置信度与来源限制，不据此宣称已经确认致命武器。

验证：7 项完整哈希与分类边界测试、34 项死亡观察器测试通过。原生坦克来源 30 项自有内存回放通过。标签对齐与来源/敌人配对是独立问题，仍不能从分别统计的两个总量反推出每个敌人由哪把武器击杀。
